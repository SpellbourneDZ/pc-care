# SPE-63: журнал исполнения и проверка Windows Recycle Bin

Статус: **в разработке**. Исполнение реальной очистки не подключено к IPC. `execute_plan` сохраняет границу SPE-62: нативные findings нельзя удалить через приложение. Подготовленные слои ниже сами по себе не разрешают системные операции.

## Подготовлено

- `domain/execution.rs`: проверка backend-плана, последовательная обработка, per-item результаты, отмена между элементами и отдельное состояние неизвестного исхода.
- `win/adapters/execution_journal.rs`: ограниченный локальный журнал без путей и содержимого файлов. Перед эффектом сохраняется `Started`, после подтверждения адаптера — результат. Временная запись синхронизируется и атомарно заменяет прежнюю; ошибка записи останавливает дальнейшие эффекты.
- `win/adapters/execution.rs`: один фоновый batch, эксклюзивная файловая lease между экземплярами, получение результата и запрос отмены. Терминальный результат публикуется после освобождения lease.
- При восстановлении `Started` становится `Unknown`, оставшиеся `Pending` — `Skipped/Interrupted`. Повторный запрос с прежним plan ID возвращает сохранённый результат и не повторяет эффект. Автоматического resume/retry нет.
- Recycle не считается освобождением места: даже подтверждённый перенос в корзину оставляет `actual_reclaimed_bytes` неизвестным. В dry-run эффекты не вызываются, reclaimed bytes равны нулю.
- `FilePolicy::reserve` повторяет проверки snapshot и возвращает RAII-объект с дескрипторами файла и всех каталогов пути. Анализатор удерживает его до окончания публикации кандидата; обычный `revalidate` освобождает сразу после проверки. Это не разрешение на перенос или удаление.

Журнал ограничен 64 записями по 256 КиБ и 500 элементами в плане. Очистка журнала и пользовательская история пока не реализованы; при исчерпании лимита возвращается `Capacity`. Неизвестная версия, некорректные данные, redirect/hardlink или lock приводят к отказу, а не сбросу файла. Это журнал приложения, не защита от другого процесса с полным доступом того же пользователя.

## Удержание проверенного пути

Regression test выявил, что открытие каталога только с `FILE_READ_ATTRIBUTES` не блокировало новый дескриптор с правом `DELETE`, несмотря на отсутствие `FILE_SHARE_DELETE`. Теперь все каталоги пути открываются также с `FILE_LIST_DIRECTORY`. Исправлен и общий `directory_guard`, который используют настройки и журнал исполнения. При отсутствии права чтения каталога операция завершается отказом; повышения прав нет.

Тесты проверяют sharing violation для файла и каждого каталога внутри fixture, запрет открытия файла для записи данных и освобождение дескрипторов после ошибки или `drop`. Интеграционный тест проверяет удержание файла во время публикации кандидата и освобождение при отключении получателя. Содержимое fixtures сохраняется; новые тесты не вызывают rename/delete.

Удержание дескрипторов не замораживает каталог: создание дочерних файлов, изменения атрибутов и другие действия через допустимые Windows-права требуют отдельных проверок. Документация [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) отдельно оговаривает, что share mode не распространяется на запросы доступа к атрибутам. Поэтому этот шаг не закрывает всю гонку исполнения. До эффекта по-прежнему нужны актуальные settings/process/policy, защищённое staging-пространство и durable mapping; закрыть дескриптор и удалить исходный путь через COM недостаточно.

## Изолированный эксперимент

`vm-recycle-probe` — отдельная dev feature и example `vm_recycle_probe`. Он не зарегистрирован в IPC, не получает пути от вызывающей стороны и не входит в обычную сборку. До создания файлов проверяются точные SMBIOS manufacturer/product `PC Care VM` / `Disposable test VM`. Маркер защищает от случайного запуска на хосте; он не доказывает изоляцию VM и не заменяет проверку её конфигурации.

После проверки маркера example создаёт собственные fixtures внутри нового UUID-каталога `target/vm-probes` относительно compile-time workspace. Проверяются файл с handle без `FILE_SHARE_DELETE`, файл после закрытия handle и экспериментальный перенос по handle перед COM. Последний случай дополнительно проверяет сохранение file ID, отказ перезаписи существующего назначения и неизменность нового файла, созданного по прежнему пути. Сохраняются HRESULT, callbacks и наличие файлов. Нет `DeleteFile` или permanent-delete fallback. Перенос по handle проверен на fixtures в VM, но не подключён к приложению.

Сборка: `cargo build --locked --example vm_recycle_probe --features vm-recycle-probe`. Запускать только в одноразовой Windows VM со snapshot перед сценарием. На основном ПК проверен только отказ firmware guard, без создания probe-каталога. Исходник GUI-обработчика и воспроизведение описаны в [VM-kit](SPE-63-vm-kit.md).

Для локальной VM установлен QEMU 11.1.0, используется программная эмуляция TCG: аппаратная виртуализация хоста выключена. Гостевой диск — отдельный qcow2; физические диски и общие папки хоста не подключены. Тестовые EXE и generated types передаются на read-only ISO с SHA-256 manifest. Тесты запускаются явно через GUI-обработчик; автозапуск, изменение реестра и обход UAC не используются. Отчёт извлекается чтением виртуального диска без записи.

Гостевая ОС: официальный Windows 10 Enterprise LTSC Evaluation ISO, SHA-256 `E4AB2E3535BE5748252A8D5D57539A6E59BE8D6726345EE10E7AFD2CB89FEFB5`, проверенный по [списку Microsoft](https://download.microsoft.com/download/c/1/1/c11d2ca5-967c-45c0-bc7d-2d9ca3f1fe07/Windows10Enterprise22H2HashValues.pdf). В госте отображается `Windows License is expired`; активация не подтверждена. Это ограничение окружения, а не пройденная проверка поддерживаемых Windows 10/11. Изменение часов и обход лицензирования не выполнялись.

Также прошли QA build и 2 native IPC tests настроек/анализа на искусственном профиле. [Результат проверок](evidence/spe-63/windows-host-reservation.md). Hosted CI исходного head `b48f315` прошёл; новые изменения требуют отдельного CI run.
- Первый запуск внутри Windows VM: 57 Rust tests, 0 failed/ignored. Это версия до добавления теста противоречивых результатов; её отчёт не заменяет проверку последней сборки.
- Первый COM-эксперимент в VM: удерживаемый handle → `COPYENGINE_E_SHARING_VIOLATION_SRC` (`0x80270027`), файл остался на месте; закрытый handle → положительный HRESULT `0x00270008`, callback с recycle item, исходного файла нет. [Отчёт](evidence/spe-63/windows10-recycle-probe.json) и [manifest EXE](evidence/spe-63/payload-safety-v2.manifest.json). Это подтверждает базовый recycle на fixtures, но не закрывает гонку для executor.
- Третий COM-случай на отдельном overlay от дискового checkpoint: `SetFileInformationByHandle(FileRenameInfo)` сохранил file ID, отказал при существующем назначении, не затронул replacement по прежнему пути; staged fixture успешно recycled. [Отчёт](evidence/spe-63/windows10-staged-recycle-probe.json) и [manifest EXE/исходников](evidence/spe-63/payload-safety-v4.manifest.json). Это проверка механизма на fixtures, не доказательство безопасности ещё не собранной полной цепочки.
- После первого COM-сценария восстановлен snapshot `pccare-before-com-probe`, NIC гостя отключён. Следующий snapshot записался, но QMP перестал отвечать; VM остановлена после диагностики и образ проверен без repair (`No errors were found`). Новая VM использует отдельный overlay от проверенной дисковой базы без сети; см. VM-kit.
- На отдельном чистом overlay прошли актуальные **60 Rust tests, 0 failed/ignored**, включая межпроцессный сценарий. [Отчёт](evidence/spe-63/windows10-unit-60.txt), [manifest](evidence/spe-63/payload-safety-v5.manifest.json). Перед этим найден и исправлен read-only атрибут копируемых с ISO bindings; до исправления обработчик отказал до запуска тестов, этот запуск не засчитывался.
- До подключения executor нужны повторная policy/settings/process revalidation, решение гонки между последней проверкой identity и COM-операцией, реальное подтверждение в UI, progress/cancel/result и проверки всей цепочки на fixtures в VM.
- Восстановление после потери питания и матрица Windows 10/11, обычного пользователя, DPI, install/uninstall остаются отдельными непроверенными сценариями. Тесты с искусственными callback-эффектами не считаются тестами реального удаления.

Задача остаётся `In Progress`, без `Done` и без заявления о готовности очистки.
